End-to-End CI/CD Pipeline for a Calculator REST API

Student: chandrahas121  ·  Repository: https://github.com/chandrahas121/spe_miniProject  ·  Docker Hub: https://hub.docker.com/r/chandrahas121/calculator

1. Overview

A small calculator REST API written in plain Java (the JDK's built-in HTTP server, built with Maven, tested with JUnit 5) is wrapped in a fully automated pipeline. A push to GitHub starts a Jenkins pipeline that builds the code, runs the tests, builds a Docker image, pushes it to Docker Hub and deploys it with Docker Compose behind an nginx reverse proxy, without any manual step. The application is deliberately simple; the effort went into the automation around it.

5. Containerization and deployment

  • Dockerfile (multi-stage): a maven:3.9-eclipse-temurin-21 stage builds the JAR (pom.xml is copied first so the dependency layer is cached until the pom changes); the runtime stage is eclipse-temurin:21-jre-alpine and copies only the JAR. It runs as a non-root user, has an explicit EXPOSE 8081, uses the exec-form ENTRYPOINT so docker stop reaches Java, and a .dockerignore keeps the build context small. A single docker run -p 8081:8081 serves the API.
  • Compose (docker-compose.yml): service calculator with 2 replicas, a health check on /actuator/health, restart: unless-stopped and a PORT environment variable; service nginx (port 8088) that waits for healthy replicas and balances round-robin (the X-Upstream header shows which replica answered); a user-defined network calculator-net. One docker compose up -d starts everything.
  • Checked behaviour: a second up -d changes nothing; a new image tag recreates only the calculators while nginx keeps serving; a crashed replica is restarted automatically.

6. Git practices

Work was split into feature branches (feature/calculator-api, feature/docker-compose, feature/jenkins-pipeline, feature/report), each merged into main with a merge commit, using small commits with plain messages. .gitignore excludes target/, IDE files, .env and keys. No credential is in the repository: the Docker Hub token and the notification address exist only in the Jenkins credentials store.

7. Challenges faced and how they were solved

ProblemSolution
Jenkins already occupies port 8080.App on 8081 inside the container, nginx published on 8088.
Docker pulls failed on the development machine: its Docker config pointed to a missing credential helper (docker-credential-desktop).The pipeline uses its own DOCKER_CONFIG folder in the workspace, so it does not depend on any user-level Docker config.
Jenkins could not run docker (permission denied).Added the jenkins user to the docker group and restarted the service.
Compose derived the project name from the folder name. The Jenkins workspace has a different folder name, so a deploy would have started a second stack fighting for port 8088.Fixed the project name (name: calculator-devops) in the compose file.
nginx resolved the replica addresses only at start-up, so after a redeploy (new container IPs) it kept pointing at dead addresses.Variable proxy_pass with Docker's resolver (127.0.0.11, 5 s validity), so addresses are re-resolved while running.
Gmail refuses normal account passwords for SMTP (error 535). Jenkins' "Test configuration" button does not save the settings, so the first build fell back to localhost:25.Use a Google app password (needs 2-step verification) and press Save after the test. The mail step is wrapped in try/catch so a mail problem never fails the deploy.
A pipeline cannot be fully tried without running it.The Jenkinsfile was validated with Jenkins' declarative linter and run once in a disposable Jenkins container with dummy credentials, confirming stage order, credential masking, JUnit publishing and the failure path before the real run.
